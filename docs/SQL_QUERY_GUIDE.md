# PostgreSQL Query Guide

This guide explains the examples in `db/postgres/queries.sql` in plain language for the project report and viva. Run the SQL files in the order listed in the [README](../README.md), including `seed.sql` before `queries.sql`.

## Safe write examples

The first block demonstrates `INSERT`, `UPDATE`, and `DELETE` on a temporary coupon. The statements are enclosed by `BEGIN` and `ROLLBACK`, so the example does not leave a coupon in the database. The insert uses `ON CONFLICT DO NOTHING` to avoid failing if the demo row already exists.

This is useful for showing that a transaction groups related changes: until `COMMIT`, they can be undone together with `ROLLBACK`.

## Wallet balances and exchange history

The customer wallet query reads `customer_wallet_summary`, which joins each wallet to its program and merchant. It filters to Asha's account and sorts by business and program name. Using the view keeps the page query short and gives the same balance columns to the customer API.

The exchange history query joins `programs` twice. The `source` alias looks up the source program, and `destination` looks up the destination program. The aliases let one query show both ends of each exchange, alongside points debited, points credited, and the settlement amount captured at exchange time. Results are newest first.

## Monthly merchant settlements

The settlement query joins `settlements` to `merchants` twice so the numeric debtor and creditor IDs display as business names. One row is the aggregate owed in one direction for a calendar month and currency. The amount sums individual exchange amounts generated by the database function; the status shows whether the month’s total is pending, paid, or cancelled.

## Aggregates: `GROUP BY` and `HAVING`

The customer points query groups wallet rows by customer. `SUM` adds their points across wallets, `COUNT` counts wallets, and `AVG` calculates the mean balance. `GROUP BY` is needed because these values summarize multiple rows per customer. `ORDER BY total_points DESC` ranks customers from most points to fewest.

The redemption summary query groups by merchant and uses `HAVING` to keep only merchants with at least one redemption. `WHERE` filters source rows before grouping; `HAVING` filters the grouped results after `SUM` has been calculated.

## `NOT EXISTS` coupon lookup

The active-coupon query returns coupons that have not expired and for which a matching row does not exist in `user_coupons` for Asha. The inner query is correlated because it compares each candidate coupon’s ID with the claim table. `NOT EXISTS` expresses the “not already claimed” rule and avoids returning duplicates that a normal join could create.

## PostgreSQL full-text search

The search example builds a `tsvector` from coupon title, description, and category, then compares it with `plainto_tsquery('english', 'pastry drink')` using `@@`. PostgreSQL's English text rules normalize words for matching. `COALESCE` turns nullable text into an empty string so concatenation still works.

`ts_rank` assigns a relevance score, and `ORDER BY relevance DESC` shows stronger matches first. The expression matches the GIN index in `db/postgres/views_indexes.sql`, allowing PostgreSQL to speed up larger searches without changing the query's meaning.

## Wallet balance audit history

The audit query reads the rows written by the wallet balance trigger. It shows when a balance changed, the wallet, the old and new values, and—when known—the account that caused the change. A `LEFT JOIN` keeps audit rows even if `changed_by` is null, such as an opening balance created during seeding.
